# Milestone 2 - API Exposure, Continuation Surface, And Memory Handoff

## Goal

Expose the real Clarification Node through `/chat` so the frontend can display the generated question as a normal assistant message, while leaving durable conversation memory open for the later memory branch.

This milestone should make the user-facing flow coherent:

```text
User asks ambiguous request
  -> /chat
  -> Input Processor
  -> Intent Classifier
  -> Clarification Node
  -> API returns clarification_required with assistant message
  -> Frontend displays the assistant question
  -> User answers through the same composer
```

The later memory branch should be able to persist and reload:

- `messages`
- `conversation_summary`
- `clarification_round_count`
- prior request context needed for clarified query reconstruction

without rewriting the Clarification Node.

## Current Baseline After Milestone 1

Assume milestone 1 has completed:

- `app/clarification/node.py` exists.
- `ambiguous` routes to the real clarification node.
- The node appends an `AIMessage` to `messages`.
- `clarification_round_count` exists in graph state.
- Clarification emits safe Langfuse metadata.

The current pre-milestone-2 API still has these limitations:

- `app/api/routes.py` returns the input-processing payload.
- It does not return graph outcome status.
- It does not return assistant messages produced by the graph.
- It does not accept or load durable conversation state.
- The frontend currently creates a generic success message instead of rendering backend assistant content.

## Scope

In scope:

- Add a stable API response shape for graph outcomes.
- Return the clarification question from graph state.
- Update frontend API types and chat rendering behavior.
- Preserve backward-compatible input-processing fields where useful for debugging.
- Add test coverage for ambiguous requests at API and frontend-adjacent boundaries.
- Add trace status updates for `clarification_required`.
- Define the memory handoff contract clearly.

Out of scope:

- Durable conversation storage.
- Production session store selection.
- Long-term storage of uploaded files.
- Final response node implementation.
- Full LangGraph checkpoint/resume infrastructure.
- Human escalation.

## Minor Architecture Adjustment

Make `/chat` return an explicit `status` field.

Reason:

- The current response only has `success` and `message`, which cannot cleanly distinguish "input processed" from "clarification required" or future "answer completed".
- The frontend should not infer graph state from node names or debug payloads.
- Observability also benefits from the same status vocabulary.

Recommended statuses:

```text
completed
clarification_required
input_failed
classification_error
system_error
```

This is compatible with the architecture's conceptual API contract:

```text
/chat
  -> clarification_required
  -> completed
  -> error
```

## Task 1 - Define The Chat Response Contract

Create or update a typed response contract for `/chat`.

Files:

- `app/api/routes.py`
- optionally `app/contracts/chat.py` if the response shape should be reusable
- `tests/api/test_chat.py`
- `frontend/src/lib/api.ts`

Recommended response shape:

```json
{
  "success": true,
  "status": "clarification_required",
  "message": "I can help with that. Which certificate do you mean, and which state are you applying in?",
  "assistant_message": {
    "role": "assistant",
    "content": "I can help with that. Which certificate do you mean, and which state are you applying in?"
  },
  "attachment_statuses": [],
  "warnings": [],
  "normalized_input": {},
  "intent": {
    "type": "ambiguous",
    "confidence_score": 0.65
  },
  "conversation_id": null
}
```

Guidance:

- Keep `message` as the display-safe user-facing text.
- Add `assistant_message` so the frontend can render graph-generated assistant content directly.
- Keep `normalized_input` only as long as the local debugging workflow needs it.
- Do not expose full `intent_decision.query` by default.
- Do not expose raw messages, raw summaries, documents, prompts, or full retrieved context.

Acceptance:

- Existing success and error tests are updated intentionally.
- Ambiguous graph result returns `status: "clarification_required"`.
- The response message is the clarification question generated by the node, not a generic API message.

Memory branch handoff:

```text

  -> identify conversation_id
  -> memory_read

  -> input processing for current turn
  -> graph invoke
  -> memory_write
  -> /chat response
```

Acceptance:

- Current code has a clear place to pass memory fields into `invoke_intent_retriever_graph`.
- No clarification logic depends on frontend-only local history.
- Docs state exactly what the memory branch must persist.

## Task 7 - Plan Query Reconstruction For The Memory Branch

Clarification can be displayed in this branch, but full clarified retrieval requires persisted conversation state.

Files:

- `docs/architecture/clarification-node/architecture.md`
- `docs/architecture/state-flow.md`
- future memory implementation docs

Required later behavior:

```text
effective query =
original request
+ assistant clarification question
+ user clarification answer
+ relevant multimodal content from the current request context
```

Implementation guidance:

- Do not make the Clarification Node mutate `normalized_input`.
- Use the memory/checkpoint layer or a dedicated query reconstruction helper before the second classification/retrieval pass.
- Keep reconstruction deterministic and idempotent.
- Preserve attachment-derived context without requiring the user to re-upload files.
- Do not persist raw uploaded bytes; persist only allowed derived context if the privacy decision permits it.

Recommended helper for later branch:

```text
app/memory/clarification_context.py
  -> load active clarification context
  -> merge original request and clarification answer
  -> expose messages/summary/counter to graph
```

Alternative if memory is not ready:

- Accept that the follow-up answer may be classified using only its own text.
- Keep this limitation explicit in the PR notes.
- Do not pretend the seamless clarified retrieval loop is complete.

Acceptance:

- The milestone 2 docs clearly identify query reconstruction as a memory/checkpoint dependency.
- The Clarification Node remains unchanged by the future reconstruction implementation.

## Milestone 2 Done Means

- `/chat` can return a real clarification question.
- The frontend displays that question as an assistant message.
- Langfuse root traces show `clarification_required`.
- The API does not duplicate clarification reasoning.
- The graph remains the source of the clarification message.
- The response contract is ready for conversation memory.
- Durable memory/checkpointing and multimodal query reconstruction are explicitly handed off to a later branch.

## Final Handoff To Memory Branch

The memory branch should implement:

- conversation/session identity
- message persistence and windowing
- conversation summary persistence/update
- `clarification_round_count` persistence/reset
- active clarification context persistence
- allowed derived attachment context persistence, if approved
- deterministic clarified query reconstruction
- trace linkage across related `/chat` requests

The memory branch must not:

- persist raw uploaded files
- rely on frontend-only conversation history as authoritative backend state
- infer clarification rounds from natural language
- require users to re-upload the same document solely because clarification happened
