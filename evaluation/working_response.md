# Response Node Evaluation Working Guide

This guide explains how the Response Node evaluation works, how the LLM-as-a-judge system assesses citizen-facing replies, where results are stored, and how to execute the runners and publish results to Langfuse.

---

## 1. Overview & Purpose

The Response Node evaluation assesses the quality, grounding, accuracy, and safety of the final answers generated by the chatbot. 

Instead of relying solely on surface-level text similarity (such as BLEU or ROUGE), it employs an **LLM-as-a-Judge** approach (using `gpt-4o-mini` at `temperature=0.0`) to independently evaluate 6 distinct quality dimensions:

1. **Correctness** – Factual accuracy compared against ground truth key points.
2. **Faithfulness** – Grounding in the retrieved document chunks (detecting hallucinations).
3. **Relevance** – Directness and focus in answering the specific citizen query.
4. **Completeness** – Coverage of essential requirements, fees, eligibility, or procedures.
5. **Citation** – Presence and correctness of source references.
6. **Safety** – Avoidance of fabricated policies/fees and responsible handling of insufficient context.

## 3. The 6 Evaluation Criteria

| Criterion | Evaluator File | What it Evaluates | Important Principles |
|---|---|---|---|
| **Correctness** | `correctness.py` | Does the response provide factually accurate information according to the expected key points? | Does not penalize concise answers if the facts are accurate. Compares strictly with ground truth. |
| **Faithfulness** | `faithfulness.py` | Are the response's claims strictly grounded in the retrieved context chunks? | Penalizes claims not found in context even if they sound plausible. Detects hallucinations and contradictions. |
| **Relevance** | `relevance.py` | Does the response directly address the user's specific query? | Penalizes off-topic rambling, irrelevant history, or misunderstandings of user intent. |
| **Completeness** | `completeness.py` | Does the response cover all essential points needed to answer the question? | Completeness does not mean maximum word count. A crisp answer covering all key points scores 1.0. |
| **Citation** | `citation.py` | Are source citations present, relevant, and accurate? | Evaluates both citation presence (attributing evidence) and citation correctness (the link/source truly backs the claim). |
| **Safety** | `safety.py` | Does the response avoid misleading guidance and fabricated procedures/fees? | In insufficient-context cases, an honest admission that details are unavailable scores 1.0; inventing fees/rules scores 0.0. |

---

## 4. Scoring Scale & Pass Threshold

All response evaluators share a standardized normalized scale from `0.0` to `1.0`:

- **1.0 (Fully satisfies)**: Perfect, fully accurate, grounded, and safe.
- **0.8 (Mostly satisfies)**: Good response with minor imperfections.
- **0.6 (Partially satisfies)**: Adequate but has notable omissions or slight ambiguities.
- **0.4 (Significant problems)**: Substantial inaccuracies, ungrounded claims, or partial answers.
- **0.2 (Mostly fails)**: Severely flawed, misleading, or largely ungrounded.
- **0.0 (Complete failure)**: Completely wrong, hallucinated, irrelevant, or unsafe.

### Case Pass Rule
A case is marked as **Passed** if:
1. `average_score >= 0.70` across the evaluated criteria, **AND**
2. `safety_score >= 0.60` (if safety is evaluated). A case that produces unsafe advice automatically fails regardless of its average score.

## 5. Dataset

The response evaluation dataset is located at:

```text
evaluation/datasets/response/cases.jsonl
```

Each line is a JSON object with the following schema:

```json
{
  "id": "RESP-001",
  "query": "Why do Indian citizens need a passport when leaving India?",
  "context": [
    {
      "chunk_id": "travel-immigration-documents__indian-passport__india__source-001__chunk-0001",
      "text": "All Indian citizens who depart or intend to depart from India are required to be in possession of a valid Passport...",
      "source_url": "https://www.passportindia.gov.in/psp/GettingStarted"
    }
  ],
  "expected_answer": {
    "key_points": [
      "Indian citizens who depart or intend to depart from India are required to possess a valid passport or travel document."
    ]
  },
  "expected_citations": [
    "https://www.passportindia.gov.in/psp/GettingStarted"
  ],
  "metadata": {
    "document": "indian-passport",
    "question_type": "purpose"
  }
}
```

## 6. How to Run the Evaluation

Ensure your virtual environment is activated and `.env` contains your `OPENAI_API_KEY`:

```powershell
.\.venv\Scripts\Activate.ps1
```

### Option A: Quick Test (Subset of Cases)
To run a fast test on the first 3 cases without sending telemetry to Langfuse:

```powershell
python -m evaluation.runners.run_response --limit 3 --no-langfuse
```

### Option B: Evaluate Specific Criteria
To focus on specific criteria (e.g., correctness and faithfulness):

```powershell
python -m evaluation.runners.run_response --criteria correctness,faithfulness --limit 5 --no-langfuse
```

### Option C: Complete 50-Case Evaluation with Langfuse
To evaluate the full dataset and upload traces/scores to your Langfuse project:

```powershell
python -m evaluation.runners.run_response --langfuse
```

## 7. Publishing to Langfuse

The evaluation results can be published in several ways:

1. **Automatic during run**: Use `--langfuse` when executing `run_response.py`.
2. **Publish existing report**: If you already generated `latest.json` using `--no-langfuse`, upload it directly:
   ```powershell
   python -m evaluation.langfuse_reporting evaluation/reports/response/latest.json --name response
   ```
3. **Batch sync all reports**: To sync Input Processor, Intent, Retrieval, and Response reports in one command:
   ```powershell
   python -m evaluation.publish_all_reports
   ```

In Langfuse, each case creates an observation trace under `evaluation:response` with individual numeric scores for:
- `average_correctness`
- `average_faithfulness`
- `average_relevance`
- `average_completeness`
- `average_citation`
- `average_safety`
- `overall_score`
- `pass_rate`

## 9. Automated Testing

Offline unit tests use mock LLM responses to test the evaluator logic without incurring API fees or network latency:

```powershell
python -m pytest tests/test_response_evaluators.py
```

Tests verify:
- Score boundary validation in `JudgeResult`.
- Markdown code block and raw JSON parsing.
- Error handling on malformed LLM output (`JudgeEvaluationError`).
- Isolated functionality of all 6 evaluators.
- Safety threshold gating in `evaluate_response_case`.
- Statistical calculations in `summarize_response_results`.
