# Response Evaluators

## 1. Purpose

The `evaluation/evaluators/response/` directory contains the LLM-as-a-judge evaluators used to assess the quality of the final response generated by the RAG chatbot.

The response evaluation receives:

- User query
- Retrieved context
- Generated response
- Expected answer / key points
- Expected citations

The evaluators determine whether the generated response is:

1. Correct
2. Faithful to retrieved context
3. Relevant to the query
4. Complete
5. Properly cited
6. Safe

---


# 3. `llm_judge.py`

## Responsibility

`llm_judge.py` is the shared LLM-as-a-judge engine.

It contains the common functionality required by all response evaluators, such as:

- Calling the judge LLM
- Supplying the evaluation prompt
- Passing the query, context, generated response, and expected information
- Requesting structured output
- Parsing the judge result
- Validating the returned score
- Handling judge errors

The individual evaluators should not duplicate this common LLM-calling logic.

## Conceptual Flow

```text
Evaluator
    ↓
llm_judge.py
    ↓
Judge LLM
    ↓
Structured evaluation result
    ↓
Score + reasoning
```

## Expected Interface

A shared function should conceptually support:

```python
run_llm_judge(
    criterion,
    query,
    context,
    generated_response,
    expected_answer=None,
    expected_citations=None
)
```

The exact implementation can depend on the LLM provider and framework used by the project.

## Expected Judge Output

The judge should return a structured result rather than free-form text.

Example:

```json
{
  "score": 0.9,
  "reason": "The response correctly answers the question but omits one expected point."
}
```

Recommended score range:

```text
0.0 – 1.0
```

The evaluator should also preserve the judge's reasoning because it is useful for debugging and manual validation.

# 4. `correctness.py`

## Objective

Determine whether the generated response provides factually correct information according to the expected answer and the supplied context.

## Inputs

```text
Query
Retrieved Context
Generated Response
Expected Answer
```

## Questions for the Judge

The evaluator should determine:

- Does the answer correctly answer the question?
- Are the factual claims accurate?
- Does the answer agree with the expected key points?
- Does it introduce factual claims that contradict the provided information?
- Does it contain important factual errors?

## Important Principle

Correctness is not based only on whether the response sounds plausible.

The evaluator should compare the response against the evaluation ground truth and supporting context.

## Output

```json
{
  "score": 0.0,
  "reason": "..."
}
```

---

# 5. `faithfulness.py`

## Objective

Determine whether the generated response is supported by the retrieved context.

Faithfulness focuses on whether the chatbot stays grounded in the information retrieved from the knowledge base.

## Inputs

```text
Query
Retrieved Context
Generated Response
```

## Questions for the Judge

The evaluator should determine:

- Are the response's claims supported by the retrieved context?
- Does the response introduce information that cannot be found in the context?
- Does it make unsupported assumptions?
- Does it hallucinate facts?
- Does it contradict the retrieved information?

## Important Principle

A response can be relevant but unfaithful.

For example:

```text
Query:
"What documents are required?"

Response:
"Bring Aadhaar, PAN, passport and two photographs."

Context:
Only Aadhaar and passport are mentioned.
```

The response may sound reasonable, but the additional claims are unsupported by the retrieved context.

---

# 6. `relevance.py`

## Objective

Determine whether the generated response directly addresses the user's query.

## Inputs

```text
Query
Generated Response
```

Context may also be supplied when useful.

## Questions for the Judge

The evaluator should determine:

- Does the response answer the actual question?
- Does it stay focused on the user's request?
- Does it contain unnecessary information?
- Does it go off-topic?
- Does it misunderstand the user's intent?

## Example

```text
Query:
"What is the fee for an Indian passport?"

Good:
"The applicable passport fee depends on the passport type and service category..."

Poor:
"A passport is an important travel document. India introduced passports under..."
```

The second response may contain correct information but does not directly answer the question.

---

# 7. `completeness.py`

## Objective

Determine whether the generated response covers the important information expected for the query.

## Inputs

```text
Query
Generated Response
Expected Answer
Retrieved Context
```

## Questions for the Judge

The evaluator should determine:

- Are the important expected key points included?
- Does the response omit an important requirement?
- If the query contains multiple parts, are all parts answered?
- Is the answer sufficiently complete without requiring unnecessary information?

## Important Principle

Completeness does not mean maximum length.

A concise answer can be completely sufficient if it contains all important points.

## Example

Expected key points:

```text
- Applicant must be an Indian citizen
- Applicant must be 18 or older
- Form 6 is used
```

If the response only says:

```text
"You can register using Form 6."
```

the response may be relevant but incomplete.

---

# 8. `citation.py`

## Objective

Determine whether citations are present, appropriate, and supported by the supplied sources.

## Inputs

```text
Query
Generated Response
Retrieved Context
Expected Citations
```

## Questions for the Judge

The evaluator should determine:

- Does the response provide citations when citations are expected?
- Do the cited sources correspond to the information being claimed?
- Are the citations relevant to the answer?
- Are important claims supported by appropriate sources?
- Does the response cite an unrelated source?
- Does the response invent citations?

## Important Principle

Citation quality has two aspects:

```text
Citation presence
        +
Citation correctness
```

A response containing a citation is not automatically correctly cited.

---

# 9. `safety.py`

## Objective

Determine whether the response avoids unsafe, misleading, or unsupported guidance.

The chatbot deals with government-document application information, so responses should avoid presenting uncertain information as authoritative.

## Inputs

```text
Query
Generated Response
Retrieved Context
Expected Answer
```

## Questions for the Judge

The evaluator should determine:

- Does the response provide unsafe guidance?
- Does it confidently invent requirements, fees, deadlines, or procedures?
- Does it present unsupported information as fact?
- Does it appropriately acknowledge when the provided context is insufficient?
- Does it avoid misleading the user?

## Insufficient-Context Cases

Some evaluation cases intentionally do not provide enough information to answer a question.

For these cases, the correct behavior is to avoid inventing an answer.

Example:

```text
Expected behavior:
insufficient_context_refusal
```

The evaluator should reward a response that clearly states that the available information does not specify the requested detail.

It should penalize a response that invents a fee or requirement.

---

# 10. Common Evaluation Input

The six evaluators should use a consistent evaluation data model wherever possible.

```text
query
context
generated_response
expected_answer
expected_citations
metadata
```

Example:

```json
{
  "query": "What documents are required for a passport application?",
  "context": [
    {
      "chunk_id": "example-chunk",
      "text": "Supporting documents include...",
      "source_url": "https://example.gov.in"
    }
  ],
  "generated_response": "You need...",
  "expected_answer": {
    "key_points": [
      "Proof of date of birth",
      "Proof of identity",
      "Proof of residence"
    ]
  },
  "expected_citations": [
    "https://example.gov.in"
  ]
}
```

# 11. Evaluator Independence

Each evaluator measures a different quality dimension.

```text
Correctness
    ↓
Is the answer factually correct?

Faithfulness
    ↓
Is the answer grounded in retrieved context?

Relevance
    ↓
Does it answer the user's question?

Completeness
    ↓
Does it cover the important expected points?

Citation
    ↓
Are claims appropriately supported by citations?

Safety
    ↓
Does it avoid unsafe or misleading guidance?
```

These dimensions should not be treated as interchangeable.

A response can:

- Be relevant but incomplete
- Be correct but poorly cited
- Be complete but unfaithful to the retrieved context
- Be relevant and fluent but unsafe because it invents information

---

# 12. LLM-as-a-Judge Prompt Design

Each evaluator should provide criterion-specific instructions to the judge.

The prompt should clearly identify:

```text
1. Evaluation criterion
2. User query
3. Retrieved context
4. Generated response
5. Expected answer, where applicable
6. Expected citations, where applicable
7. Scoring requirements
8. Required output format
```

The judge should be instructed to evaluate only the specified criterion.

For example, the correctness evaluator should not lower a correctness score merely because the answer is verbose if the information is factually correct. Relevance and completeness evaluate different properties.

---

# 13. Structured Output

The judge should return machine-readable output.

Recommended structure:

```json
{
  "score": 0.85,
  "reason": "The response is mostly correct but misses one expected requirement."
}
```

The runner can then use the score for aggregation while retaining the reasoning for inspection.

If the chosen LLM framework supports structured output or a schema, it should be preferred over parsing arbitrary natural-language responses.

---

# 14. Score Scale

All response evaluators should use the same normalized scale:

```text
0.0 = Complete failure
0.2 = Mostly fails
0.4 = Significant problems
0.6 = Partially satisfies
0.8 = Mostly satisfies
1.0 = Fully satisfies
```

Intermediate values may be used when appropriate.

The scoring definitions should be included in each evaluator's judge prompt so that the six evaluators remain consistent.

---

# 15. Error Handling

`llm_judge.py` should handle common judge failures.

Examples:

- LLM API failure
- Timeout
- Invalid structured output
- Missing score
- Score outside the 0–1 range
- Empty judge response

A judge failure should not silently become a score of `0`.

Instead, it should be represented as an evaluation error so that the runner can distinguish:

```text
Actual poor response
```

from:

```text
Evaluation system failure
```

---

# 16. Relationship With the Response Runner

The evaluators are not responsible for running the complete RAG pipeline.

The runner will coordinate them.

```text
evaluation/datasets/response/cases.jsonl
                ↓
        run_response.py
                ↓
          RAG pipeline
                ↓
       Generated response
                ↓
       ┌────────┴────────┐
       ↓        ↓        ↓
 correctness faithfulness relevance
       ↓        ↓        ↓
 completeness citation safety
       └────────┬────────┘
                ↓
        Aggregate results
                ↓
             Langfuse
```

The evaluator files should therefore focus on **evaluation**, while `run_response.py` handles orchestration.

---

# 17. Langfuse Integration Boundary

The individual evaluator files should ideally return evaluation results rather than directly managing the complete Langfuse workflow.

For example:

```python
{
    "criterion": "correctness",
    "score": 0.9,
    "reason": "..."
}
```

The runner can then publish these results to Langfuse consistently.

This keeps responsibilities separated:

```text
Evaluator
→ evaluates

Runner
→ orchestrates

Langfuse integration
→ records results
```

---

# 18. Testing the Evaluators

Before using all 50 dataset cases, test the evaluators with a small number of known examples.

Recommended initial test:

```text
3–5 cases
```

Include:

1. A clearly correct response
2. A clearly incorrect response
3. A partially correct response
4. An incomplete response
5. An insufficient-context case

Then manually inspect the judge's:

```text
Score
Reasoning
```

The goal is to verify that the judge behaves as intended before running the complete dataset.

---

# 19. Manual Validation of the Judge

After the initial implementation, manually review approximately 10–15 evaluation results.

Check:

- Is the score reasonable?
- Does the reasoning support the score?
- Is the judge too strict?
- Is the judge too lenient?
- Does it detect hallucinations?
- Does it recognize incomplete answers?
- Does it distinguish relevance from completeness?
- Does it correctly handle insufficient context?
- Does it evaluate citations appropriately?

If systematic problems are found, improve the evaluator prompts before relying on the results.

# 22. Design Principle

The response evaluation system should follow one central principle:

> **The LLM judge evaluates the chatbot; it does not replace the chatbot.**

The evaluation pipeline should therefore run against the actual RAG-generated responses and use the reviewed evaluation dataset as the ground truth/reference.

This ensures that the evaluation measures the real behavior of the application rather than a manually constructed or idealized response.
